# fanout

사용자가 반복해 쓰던 지시문을 한 명령으로 묶은 것이다.

> 고쳐야 하는 것들을 하위 세션에서 진행. 동시에 가능한 작업은 각 세션에서, `/superpowers:using-superpowers`로. 설계·구현계획은 검토를 거쳐 구현하고, 구현은 Codex gpt-6.1-sol high, 검토는 Opus 5.5 high. 지적은 `/cascade-fix:cascade-fix`로, Warning 이상은 바로 고치고 그 아래는 모아서 꼭 고칠지 다시 따진 뒤 처리. PR 생성 후 병합. 모든 하위 세션이 끝나면 이 세션에서 통합해 한 번 더 검증하고, 하위 세션 보관과 작업 파일·워크트리 정리. Codex·Cursor 전송은 모두 허용.

`/fanout`을 부른 것 자체가 위 내용 전부(하위 세션 시작, Codex·Cursor 전송, PR 병합, 보관·정리)에 대한 사용자의 승인이다. 다시 묻지 않는다. 예외는 사용량이 임계값을 넘었을 때(1절 4, 3절)뿐이다.

**예외 — 병합 제한 저장소.** 전역·프로젝트 `CLAUDE.md`가 병합·배포 원칙(직접 병합 금지, PR base 브랜치, 승인자 등)을 정해 둔 저장소는 그 원칙이 이 스킬보다 우선한다. `/fanout`의 승인은 그 원칙을 넘지 않는다.
- PR base는 그 원칙이 정한 브랜치를 쓴다. 원칙이 다른 문서(지침·규정)를 가리키면 적용하기 전에 그 문서의 해당 부분을 다시 읽는다.
- 하위 세션도 이 세션도 **PR까지만** 만든다. 병합·릴리스 태그·운영 배포는 사용자가 한다.
- 이 경우 「병합」 대신 「PR 생성·CI 통과」를 끝난 조건으로 삼고, 통합 검증(4절)은 각 PR 브랜치를 이 세션의 임시 워크트리에 합쳐 돌린다(병합 순서와 충돌 여부를 보고에 적는다). 임시 워크트리는 5절에서 지운다.

## 인자

- 인자 없음: 이 대화에서 이미 정리된 「고칠 것」 목록(진단·검토·비교 결과)을 대상으로 한다.
- 인자 있음: 인자를 대상 설명이나 바꿀 규칙으로 읽는다. 예: `/fanout 3번 빼고`, `/fanout 병합은 하지 말고 PR까지만`, `/fanout 배포까지`. 인자로 바꾼 규칙은 brief에도 반영한다. 인자로도 병합 제한 저장소 예외는 풀리지 않는다.
- 대화에 고칠 것 목록이 없고 인자도 없으면, 그때만 무엇을 할지 묻는다.

## 1. 나누기 (이 세션)

1. **전제 확인.** 프로젝트 `CLAUDE.md`·설계 문서에서 전제(누가, 몇 명이, 어떤 비용으로)를 찾는다. 없으면 묻는다. 전제를 넘는 항목은 세션을 띄우지 않고 「제안만」 목록으로 뺀다.
2. **묶기.**
   - 같은 파일(공통 레이아웃, 설정 파일, 같은 모듈)을 건드리는 항목은 한 세션으로 묶는다. 두 세션이 같은 파일을 쓰면 안 된다.
   - 한두 줄짜리 작은 항목은 따로 세션을 만들지 않고, 관련된 세션이나 「잔여 수정」 세션 하나에 모은다.
   - 다른 항목의 결과(병합된 패키지, 바뀐 API)가 필요한 항목은 **2단계**로 미룬다. 1단계 PR이 모두 병합되면 이 세션이 2단계 세션을 띄운다. 병합 제한 저장소처럼 이 세션이 병합할 수 없으면, 1단계 PR이 사용자 손으로 병합된 것을 확인한 뒤 띄운다.
   - 저장소가 다르면 세션도 다르다(`cwd`로 그 저장소를 준다).
3. **공유 노트 폴더.** `~/.claude/fanout-notes/<YYYY-MM-DD>-<묶음 이름>/`을 만들고 그 경로를 모든 brief에 적는다. 하위 세션의 인계 메모는 여기에 남긴다.
4. **사용량 확인.** `mcp__ccd_session_mgmt__get_usage`를 한 번 부른다(지연 로드 도구면 `ToolSearch`로 먼저 불러온다). `plan.status`에 따라:
   - `ok`: 한도 창(5시간·주간·모델별 주간) 중 하나라도 `percentUsed`가 80 이상이면 수치와 초기화 시각(`resetsIn`)을 보여 주고 `AskUserQuestion`으로 하나를 고르게 한다.
     - 기다리기: 초기화 시각을 알리고 하위 세션을 띄우지 않고 멈춘다.
     - 줄여서 진행: 1단계 세션만 띄우거나 세션을 더 묶어 수를 줄인다. cascade-fix 작업자를 Codex·Cursor로 돌리는 프로필이 있으면 brief에 `--profile <이름>`을 적는다.
     - 그대로 진행.
     임계값보다 낮으면 묻지 않고 「사용량: 5시간 N% · 주간 N%」 한 줄만 쓴다.
     `extraUsage`(추가 사용량의 월 한도)는 판단에도 한 줄 보고에도 쓰지 않는다. 팀 플랜에서는 이 값이 개인 사용량과 맞지 않게 나온다.
   - `unavailable`: 「사용량 확인 못 함」 한 줄만 쓰고 진행한다.
   - `not_applicable`: 아무것도 쓰지 않고 진행한다.
   데스크톱 앱에서 시작한 실행은 구독자 API 크레딧이 아니라 Claude Code 사용으로 잡히므로 API 크레딧은 선택지에 넣지 않는다.
5. **알리기.** 세션별로 「제목 — 할 일 — 건드릴 파일」 한 줄씩, 그리고 2단계와 「제안만」 항목을 짧게 보여 준다. 답을 기다리지 않고 바로 2절로 간다.

세션이 하나뿐이어도 이 절차를 따른다(이유를 한 줄 적는다. 예: 「모두 `layout.ts`를 거쳐 한 세션으로 묶었다」).

## 2. 하위 세션 띄우기

- 둘 이상이면 먼저 `mcp__ccd_session__mark_chapter`로 묶음 제목을 단다.
- 세션마다 `mcp__ccd_session__start_session`: `initiation: "user_asked"`, `context: "fresh"`, `use_worktree: true`, 다른 저장소면 `cwd`. `context: "fresh"`는 `prompt`와 함께 80자 이상의 `background`가 있어야 하고, 빠지면 호출이 거절된다. 호출 바로 앞에 굵은 제목 한 줄과 한 문장 설명을 쓴다.
- brief는 아래 틀을 채워 쓴다. `## 배경` 절은 `background`에, `## 할 일`부터 끝까지는 `prompt`에 넣는다. 이 대화에서 찾은 근거(파일:행, 커밋, 다른 저장소의 참고 구현)를 brief에 직접 적는다. 하위 세션은 이 대화를 모른다.

```markdown
## 배경
- 프로젝트 전제: <예: 운영자 1명, 소수 지인, Cloudflare 무료>
- 왜 이 작업을 하는지, 이 대화에서 찾은 것 요약
- 동시에 도는 다른 세션과 그 세션이 건드리는 파일: <경로>. 이 파일들은 건드리지 않는다.
- 공유 노트 폴더: <~/.claude/fanout-notes/...>
- 사용자에게 보이는 글, 문서, 커밋 메시지는 한국어로 쓴다. 판단이 갈리면 작은 쪽을 고른다.

## 할 일
1. <항목> — 위치 `<파일:행>`, 근거, 원하는 결과
   - 먼저 확인할 것(재현, 공식 문서), 확인 결과가 다르면 고치지 말고 보고
2. ...

범위 밖: <고치지 않을 것>

## 진행 방식 (사용자 지시)
- `/superpowers:using-superpowers`로 시작한다.
- **설계·계획:** 큰 작업은 brainstorming으로 설계(spec), writing-plans로 구현계획(plan)을 쓴다. 작은 작업은 설계와 계획을 짧은 문서 하나로 쓴다. 각 문서는 `codex-review` 스킬(`--doc`)로 검토하고 지적은 `/cascade-fix:cascade-fix`로 고친다. 검토는 최대 2회, 2회차에는 Critical만 고친다. 지적이 좁은 경계 사례로 옮겨 가면 2회 전이라도 끝낸다.
- **구현:** Codex CLI로 한다. 워크트리 루트에서 백그라운드로 실행하고 완료 알림을 기다린다(폴링하지 않는다).
  `codex exec -m gpt-6.1-sol -c model_reasoning_effort=high -s workspace-write "<계획 파일 경로와 할 일>" < /dev/null`
  `< /dev/null`을 빼지 않는다. 백그라운드 Bash의 stdin은 닫히지 않는 소켓이라, 빼면 Codex가 「Reading additional input from stdin...」에서 끝없이 기다린다.
  Codex 샌드박스는 네트워크가 막혀 시험·빌드가 실패할 수 있다. 시험·타입·빌드는 Codex가 끝난 뒤 이 세션이 직접 돌리고, diff를 직접 읽어 확인한다.
- **구현 검토:** Agent 하위 에이전트(`model: opus`, `effort: high`)로 브랜치 diff를 검토한다. Critical/Warning/Info로 나눠 받는다.
- **지적 처리:** Warning 이상은 `/cascade-fix:cascade-fix`로 바로 고친다. 그보다 낮은 지적은 모아 두었다가 전제에 비춰 꼭 고쳐야 하는지 한 번 더 따지고, 필요한 것만 고친다(이때 고르기로 한 지적은 등급 필터에 걸러지지 않게 cascade-fix에 `--severity`를 붙이지 않는다). 고치지 않은 것은 이유와 함께 보고에 남긴다. 구현 검토도 최대 2회다.
- **허용된 것:** Codex·Cursor로 코드·문서를 보내는 것은 사용자가 모두 허용했다. codex-review·cascade-fix의 전송 확인과 cascade-fix의 「계획 확인」은 묻지 않고 「진행」으로 고른 것으로 한다. PR 병합도 허용했다(병합 제한 저장소 제외 — 아래).
- **마무리:** 저장소 검사(타입·시험·빌드, 관련 e2e)를 통과시킨 뒤 PR을 만들고, CI가 통과하면 저장소 규칙대로 병합한다. 운영 배포는 저장소 규칙을 따르고, 사람이 직접 실행해야 하는 명령은 실행하지 말고 보고한다.
- **병합 제한 저장소**(전역·프로젝트 `CLAUDE.md`가 병합·배포 원칙을 정해 둔 저장소)면 그 원칙을 따른다: PR base는 <그 원칙이 정한 브랜치>, PR까지만 만들고 병합·태그·배포는 하지 않는다. <병합 제한 저장소가 아니면 이 줄을 지운다>
- 사용자 결정이 꼭 필요한 것만 묻는다. 나머지는 작은 쪽으로 정하고 보고에 적는다.

## 끝난 조건
PR이 <기본 브랜치>에 병합되었고 검사와 CI가 통과했다(병합 제한 저장소면: PR을 만들었고 검사와 CI가 통과했다). 마지막 보고에 적는다.
- PR 링크, 병합 커밋(병합 제한 저장소면 PR 헤드 커밋)
- 항목별로 고쳤는지 여부와 근거
- 검사 결과(명령과 통과 여부)
- 고치지 않은 낮은 지적과 그 이유
- 사람이 확인해야 할 것(실기기, 운영 화면, 배포 명령)
- 다음 단계 세션이 알아야 할 것은 공유 노트 폴더에 인계 메모로 남긴다
```

## 3. 기다리는 동안

- 폴링하지 않는다. 하위 세션이 턴을 끝내면 앱이 `<side-sessions-event>`로 이 세션을 깨운다. 그때마다 진행 상황을 한두 줄로 알린다.
- 하위 세션이 막혀서 물으면 이 대화와 전제로 답할 수 있는 것은 `SendMessage`로 답하고, 사용자 결정이 필요한 것만 사용자에게 묻는다.
- 하위 세션이 이용 한도로 멈췄다고 보고하거나 2단계 세션을 띄우기 전에는 1절 4의 사용량 확인을 다시 한다. 임계값을 넘었으면 같은 선택지로 묻고, 「기다리기」를 고르면 남은 세션을 그대로 두고 초기화 시각을 알린다.
- 하위 세션의 보고는 증거가 아니다. 「병합했다」는 보고는 `gh pr view <번호> --json state,mergeCommit`으로 확인한다.
- 1단계 PR이 모두 병합되면 2단계 세션을 2절대로 띄운다(필요하면 패키지 발행 같은 사이 작업을 이 세션에서 먼저 한다).

## 4. 통합 검증 (모든 세션이 끝난 뒤, 이 세션)

1. 각 PR이 병합됐는지 `gh`로 확인한다. 병합되지 않은 세션은 그 이유를 확인하고, 이어서 할 수 있으면 그 세션에 `SendMessage`로 맡긴다.
2. 이 세션의 checkout을 최신 기본 브랜치로 맞춘다(`git fetch` 후 fast-forward. 작업 중인 변경이 있으면 건드리지 말고 알린다). 병합 제한 저장소는 머리말의 예외대로 임시 워크트리에 PR 브랜치들을 합친다.
3. 합쳐진 상태로 저장소 전체 검사(타입·시험·빌드, e2e)를 돌린다. 화면이 바뀐 작업이면 브라우저로 직접 열어 확인한다. 저장소 규칙상 이 세션이 배포하는 것이 맞으면 배포하고 운영 화면을 확인한다.
4. 통합에서만 드러난 문제는 작으면 이 세션에서 고쳐 PR로 병합하고(병합 제한 저장소는 PR까지), 크면 사용자에게 알린다.

## 5. 정리

검증이 끝난 뒤에 한다. 병합되지 않았거나 사용자 확인을 기다리는 세션은 보관하지 않고 남긴다(병합 제한 저장소에서 사용자 병합을 기다리는 PR의 세션도 남긴다).

1. **하위 세션 보관:** `mcp__ccd_session_mgmt__list_sessions {"linked": true}`로 이 세션이 띄운 세션을 찾아 `mcp__ccd_session_mgmt__archive_session`으로 보관한다(`reason`에 PR 번호). 보관하면 그 세션의 워크트리도 함께 정리된다. `mcp__ccd_host__clean_up_worktrees`는 30일 넘게 쓰지 않은 세션용이라 쓰지 않는다.
2. **워크트리:** 각 저장소에서 `git worktree list`로 남은 것을 확인하고, 이번 작업에서 생겼고 병합이 끝난 워크트리(와 4절의 임시 통합 워크트리)만 `git worktree remove`한다(커밋 안 된 변경이 있으면 지우지 말고 알린다). 마지막에 `git worktree prune`.
3. **브랜치:** 병합된 로컬 브랜치는 `git branch -d`로 지운다(`-D` 쓰지 않는다). 원격 브랜치는 PR 병합 때 지워지지 않았으면 지운다.
4. **작업 파일:** 하위 세션이 저장소 밖에 만든 임시 파일(Codex 로그, cascade-fix 작업 폴더 등)과 공유 노트 폴더를 지운다. 노트에 남겨 둘 만한 내용(사람 확인 목록, 보류한 결정)은 최종 보고에 옮긴 뒤 지운다. 저장소 안 파일은 지우지 않는다.
